# Fixes v0.3.1 — Contract Unwrapping, Mesh Error Handling & Filter Bar Cleanup
Feature: v0.3.1 Fixes in Rp-app
Status: Completed

## Specs
S1 RelayApi response wrappers and DeviceInfo contract:
- `GET /v1/devices` returns `{ "devices": [ DeviceInfo ] }`. Add `DevicesResponse` wrapper in `protocol/Http.kt`, unwrap in `RelayApi.devices()`, and add `revoked: Boolean = false` to `DeviceInfo` so revoked devices are omitted from the active device list.
- `GET /v1/machines` returns `{ "machines": [ MachineSummary ] }`. Add `MachinesResponse` wrapper in `protocol/Http.kt` and unwrap in `RelayApi.machines()`.
- `GET /v1/prompts` returns `{ "prompts": [ Prompt ] }`. Add `PromptsResponse` wrapper in `protocol/Http.kt` and unwrap in `RelayApi.openPrompts()`.
- Audit all other RelayApi calls against `Rp-relay/src/http/routes` to verify contract conformance.
- Unit tests with `MockWebServer` assert exact JSON shapes and resilience to unknown extra fields; `DevicesScreenTest` verifies devices display names and "(este)" for current device.

S2 Mesh loading resilience and explicit error state:
- When the relay returns 404 (e.g. deployed relay v0.4.0 lacking `/v1/mesh`), `MeshUiState` transitions to an explicit error state: `isLoading` is set to `false`, the loading skeleton disappears, and the message "Tu relay no soporta la Red de agentes. Actualiza Rp-relay a la versión 0.5.0 o superior." is displayed alongside a "Reintentar" button.
- On other network/server errors, show a generic failure message with a "Reintentar" button, and `isLoading` is set to `false`.
- Retrying re-triggers load and, on success, renders nodes.
- Pinned with tests in `MeshScreenTest` covering 404, generic error, and retry recovery.

S3 MachineFilterBar removal on Agents screen:
- Remove the redundant `MachineFilterBar` context chips row ("Todas / Empresa / Personal") from `AgentsScreen.kt`.
- The Machine hero dropdown already provides full machine and context selection; verify all selections offered by the chips remain directly selectable via the dropdown.
- Update affected Roborazzi screenshots and add assertions proving absence of the chip row.

S4 Release preparation and documentation:
- Bump `versionName` to `0.3.1` in `app/build.gradle.kts`.
- Update `README.md` and `docs/INSTALACION.md` download links and asset names to `v0.3.1` (`rp-v0.3.1-direct.apk`, `rp-v0.3.1-fcm.apk`, `rp-direct-debug.apk`) with accurate sizes.

## Log
L1: "hay 3 temas a solucionar 1) los dispositivos emparejados no cargan 2) la red de agentes se queda cargando 3) eso que te marque en rojo hay que eliminarlo de la pantalla por que si no pierde sentido el drop down de arriba"
L2: Diagnóstico corregido para F2: La versión del relay desplegado en producción es 0.5.0 (pese a que GET /healthz reportaba 0.4.0 por una constante desactualizada en el relay). La verdadera causa raíz de que la red se quedara en 'Cargando red de agentes…' fue que `MeshSubscribe` omitía `machineId: null` debido a que `RpJson` tiene `explicitNulls = false`, mientras que el gateway del relay exige estrictamente `{ machineId: Nullable(Id) }` y rechazaba la suscripción para 'Todas las máquinas'. Se solucionó con un serializador explícito en Kotlin que envía `{"machineId":null}`, complementado con contratos para todos los fixtures `appUp`, manejo de timeout/errores WS con fallback a HTTP `GET /v1/mesh`, y recuento de referencias (ref-counting por owner) en `MeshRepository` para evitar que ViewModels obsoletos cancelen la suscripción activa.
